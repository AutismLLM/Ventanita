# v0.3 — Supervision Console (design, not code)

*Status: design proposal. Nothing here is implemented. It scopes the "v2 Hooks"
section of `buildplan.md` (multi-brand) into something buildable as v0.3.*

---

## 0. One-paragraph summary

A native Linux desktop program the business owner opens to supervise N running
Ventanita bots (one per WhatsApp Business number, "brand"). It shows an overview
(every brand, is it alive, what happened last) and a per-brand detail view
(chat list + thread, WhatsApp-style, backed by the bot's own SQLite file). It
also hosts the "add a brand" flow: spin up an isolated display, show the QR
code, calibrate, start the bot.

Recommendation: **a thin `pywebview` window around a stdlib `http.server`
serving one static HTML file**, vanilla JS, no build step. One bot process per
brand, unchanged. **One directory per brand** holding its own `config.yaml`,
`ventanita.db`, `ventanita.log`, browser profile and a `status.json` heartbeat.
The console is a **read-only poller** of those files plus a launcher of
detached processes. It is not a daemon and never sits between the bot and
WhatsApp.

## 1. What exists today (the atom, as committed at v0.2.1)

Confirmed from `src/ventanita/main.py` and `src/ventanita/db.py` at HEAD:

- One `ventanita` process = one `while True` loop = one pinned browser window =
  one WhatsApp session. `config.yaml` is loaded from the **current working
  directory** (`CONFIG_PATH = "config.yaml"`), so "which brand" is currently
  "which directory you ran it from."
- One SQLite file (`paths.db`), four tables, no `brand_id` column yet:

  ```sql
  customers(number PK, name, first_seen, notes)
  orders(id PK, customer, items, status, ts)
  menu(item, price, available)
  messages(id PK, customer, role, content, ts)   -- role: user | assistant
  ```

- `messages` is the audit trail the detail screen needs. `orders` is written on
  every sent reply that parsed an item. Nothing records "flagged, not sent"
  except the log line `Flagged, not sent (reason): ...`.
- `parser.clean(raw, number="self-chat", name="self")` — customer identity is a
  placeholder today. Every message lands under customer `self-chat`. The
  console can only show what the DB holds; per-customer threads become real
  when the bot starts keying on the chat-row label. That is bot work and is
  called out in §8 as a dependency, not console work.
- Live testing runs the browser inside **Xvfb** (`scripts/start_isolated_display.sh`,
  `DISPLAY=:99`) so pyautogui/xdotool never touch the real desktop. The QR
  link is done by screenshotting the virtual display (`qr_login.png` in the
  repo root is exactly that) and scanning it with the phone.
- `calibrate.py` = eleven "hover the mouse here, press Enter" prompts, reads
  `pyautogui.position()`, writes six keys under `window:` in `config.yaml`. On
  an Xvfb display nobody moves the mouse, so today's isolated-display setup is
  effectively calibrated by hand from screenshots.
- Kill switch: `pynput` hooks **the X display the bot process is attached to**.
  On `DISPLAY=:99` that is a display with no physical keyboard, so F9 on the
  real keyboard does not reach it. Worth stating plainly: for isolated-display
  brands, "stop the process" is the practical kill switch. The console's Stop
  button (§4) is that.

## 2. Architecture choice

### Options weighed

| Option | Deps added | UI code | Debuggable at 2am? | Verdict |
|---|---|---|---|---|
| **A. pywebview + stdlib http.server + one HTML file** | pip: `pywebview`. apt: `python3-gi`, `gir1.2-webkit2-4.1` (already present on the dev box; pywebview on Linux *is* PyGObject+WebKit2GTK underneath) | HTML/CSS/vanilla JS, ~300 lines, zero build step | Yes: `ventanita-dashboard --browser` serves the same page to Firefox with devtools; `curl localhost:PORT/api/brands` shows the raw JSON | **Recommended** |
| B. GTK4/PyGObject directly | apt: `python3-gi` (same as A minus pywebview) | Python widget tree: `Gtk.ListBox` + `Gtk.TextView` chat thread, CSS provider for bubbles. Est. 2–3× the code of A for a worse-looking result | Harder: no way to inspect state without GTK Inspector; can't run headless in tests | Rejected: more code, less familiar, no dependency win in practice |
| C. Tkinter (stdlib) | none | `Text` widget with tags for a chat thread. Doable but visibly 1998 | Yes, but the thread view will be painful and the owner will not want to look at it | Rejected: the one screen that matters most (thread) is Tk's weakest |
| D. Terminal TUI | pip: something | — | — | Rejected: the operator is not a developer |
| E. Plain browser tab, no wrapper | none beyond stdlib | same HTML as A | Yes | Rejected by requirement ("not a browser tab") — but kept as A's `--browser` fallback for free |
| F. Electron / Tauri / Qt | a runtime, a toolchain, or a 100 MB wheel | — | No | Rejected on sight |

### Why A wins for *this* project

- **The atom's dependency list does not change.** `pywebview` goes in an
  optional extra (`pip install -e ".[dashboard]"`). A kitchen PC running only
  the bot installs nothing new. The five-then-seven pip deps of the bot stay
  where they are.
- **Everything is still Python + one text file.** Server: `http.server` from
  stdlib, JSON via `json`, SQLite via `sqlite3`. The HTML file has inline CSS
  and inline JS, no npm, no bundler, no framework, no `node_modules`. The rule
  for the front-end is the same as the bot's: if it needs a build step it
  does not ship.
- **A chat-list-plus-thread UI is what HTML is for.** Two columns, a scrolling
  list, bubbles. It is the most boring possible way to render text in boxes.
  In GTK it is a project.
- **Debuggability degrades gracefully.** pywebview missing or WebKit broken?
  Run `--browser`. Page blank? `curl` the JSON. JSON wrong? Open the SQLite
  file with `sqlite3`. Each layer is inspectable with tools that already exist.
- **It launches like a real app.** pywebview gives a titled, iconed, resizable
  native window (GTK on this box), a `.desktop` file makes it appear in the
  app menu. No address bar, no tabs, no "which browser."
- **Honest cost:** pywebview drags in PyGObject + WebKit2GTK as system
  packages. That is one more `apt install` line in the README, exactly like
  `tesseract-ocr` already is. On this machine both are already installed.

### What A explicitly forbids

No React/Vue/Svelte, no TypeScript, no Tailwind, no websockets, no SPA router.
`setInterval(fetch(...), 3000)` and `innerHTML`. If the page gets big enough
that this hurts, the answer is fewer features, not a framework.

## 3. Process model

### 3.1 One process per brand, unchanged

The bot stays exactly what it is. The only change: it must be told which brand
it is, instead of assuming `./config.yaml`.

```
ventanita --config brands/tacos-el-nico/config.yaml     # or VENTANITA_CONFIG=...
```

`main.py` and `calibrate.py` resolve every relative path in `paths:` against
the config file's directory, not the CWD. That is the whole change to the loop.

### 3.2 Per-brand directory, per-brand SQLite file

```
brands/
  tacos-el-nico/
    config.yaml          # window coords, persona, display, timing, safety
    menu.txt
    ventanita.db         # this brand's customers/orders/menu/messages
    ventanita.log        # rotated daily, as today
    status.json          # heartbeat, written by the bot each tick (§3.4)
    browser-profile/     # --user-data-dir: the WhatsApp login lives here
  birria-hermanos/
    ...
```

**Decision: separate DB file per brand, not one shared DB with a `brand_id`
column.** `buildplan.md` §7 anticipated the column; this design deliberately
diverges, because:

- **The atom does not change.** `db.py` has no idea brands exist. No function
  gains a `brand_id` parameter, no test changes, no `WHERE brand_id = ?` that
  can be forgotten once and leak one brand's customer into another's prompt.
- **Isolation is free.** N bot processes each write their own file. No
  cross-process write contention, no shared lock, no "brand A's stuck
  transaction froze brand B." A corrupted DB takes one brand down, not all.
- **Operations are `cp` and `rm`.** Back up a brand: copy the directory.
  Remove a brand: delete the directory. Move a brand to another PC: copy the
  directory (the browser profile carries the WhatsApp login).
- `brand_id` still exists — it is the **directory name**. If a future
  reporting feature wants one merged table, `ATTACH DATABASE` across N files
  or a nightly export script does it without touching the bot.

Backwards compatibility: if `brands/` does not exist but `./config.yaml`
does, the console treats the repo root as a single brand named after
`config.yaml`'s parent directory. Phase 1 (§7) runs entirely in this mode.

### 3.3 How the console reads bot data

**Read-only SQLite, polled.** Nothing else.

```python
conn = sqlite3.connect(f"file:{db_path}?mode=ro", uri=True)
conn.execute("PRAGMA busy_timeout = 2000")
```

The bot adds `PRAGMA journal_mode = WAL` in `db.connect()` so a reader never
blocks the writer and vice versa (one line; without it `busy_timeout` still
makes phase 1 work, just with occasional 2 s stalls during a write).

Overview polls every 3 s, detail every 2 s. At ten brands that is a handful of
`SELECT ... ORDER BY ts DESC LIMIT 50` per second against files that are
kilobytes. No caching layer, no change notification, no IPC.

Log tail: `ventanita.log` last 50 lines, read with a plain `seek` from the end.

### 3.4 How the console knows a bot is alive: `status.json`

The bot writes this file at the top of every loop iteration and on every state
change, atomically (write `status.json.tmp`, `os.replace`). About fifteen
lines added to `main.py`, in a helper `status.write(path, **fields)`:

```json
{
  "pid": 41233,
  "display": ":99",
  "started_at": "2026-09-04T08:45:10+00:00",
  "last_tick": "2026-09-04T09:12:33+00:00",
  "state": "idle",
  "unread_badge": 0,
  "last_error": null,
  "last_flag": {"ts": "...", "reason": "over_threshold", "customer": "..."},
  "counts_today": {"replies": 14, "flagged": 1, "skipped_not_allowed": 3}
}
```

`state` is one of `off_hours | idle | reading | thinking | typing | flagged |
error`. `unread_badge` is the digit `trigger.py` already OCRs; the console does
not look at any screen.

Console-side definition of "running":

```
pid exists (os.kill(pid, 0) succeeds)
AND now - last_tick < 3 * timing.check_interval_sec     -> RUNNING
pid exists but last_tick stale                           -> STUCK   (red)
pid gone                                                 -> STOPPED
no status.json at all                                    -> NEVER STARTED
```

Phase 1 has no `status.json` yet and falls back to `pgrep -f "ventanita.*<config>"`
plus `MAX(ts) FROM messages`. Good enough to ship the screens before touching
the bot.

### 3.5 What the console may *do* to a process (and what it may not)

The console is a viewer that can press the same two buttons a human would at
a terminal. It does **not** supervise, restart, queue, or relay.

- **Start:** `subprocess.Popen([...], start_new_session=True, cwd=brand_dir,
  env={DISPLAY: brand.display, VENTANITA_CONFIG: ...})`, stdout/stderr to
  `brands/<id>/ventanita.out`. Detached, same as the shell scripts' `disown`.
  Closing the console does not kill bots.
- **Stop:** `os.kill(pid, SIGTERM)` using the pid from `status.json`. No
  handler in `main.py` means immediate exit; a mid-message `xdotool type` dies
  with it. For isolated-display brands this *is* the kill switch (see §1).
- **Peek:** grab a PNG of the brand's X display with `mss.mss(display=":99")`
  (mss already supports `display=` on Linux; it is already a dependency) and
  serve it at `/api/brands/<id>/peek.png`. "The monitor is the dashboard" —
  but on Xvfb the monitor is invisible, so this gives it back.

No auto-restart. If a bot dies, the overview turns red and the owner clicks
Start. A watchdog is punted (§8); if it ever comes, it is a systemd user unit,
not console code.

### 3.6 Networking and security

`http.server` binds `127.0.0.1` on a random free port, printed to stdout.
Nothing listens on the LAN, no auth, no TLS. The threat model is "one PC in a
kitchen." Remote viewing is punted (§8); if wanted, `ssh -L` already works.

## 4. Screens

Two screens plus one wizard. Everything is a static HTML file with three
`<section>` blocks toggled by `hidden`; no client-side router.

### 4.1 Overview (`/`)

Data: `GET /api/brands` → one JSON object per brand, built from
`status.json` + one query per DB (`last message ts`, `count today by role`,
`distinct customers with a message in last 30 min`).

```
┌──────────────────────────────────────────────────────────────────────────┐
│  Ventanita                                             [+ Add a brand]   │
├──────────────────────────────────────────────────────────────────────────┤
│  ● Tacos El Nico        :99   RUNNING  idle   up 3h 12m                  │
│    last activity 2 min ago · unread now 0 · 14 replies / 1 flagged today │
│    active chats: 3                                   [Open] [Stop] [Peek]│
├──────────────────────────────────────────────────────────────────────────┤
│  ● Birria Hermanos      :100  STUCK    last tick 4 min ago               │
│    last error 09:02  "OCR confidence 0.31 below threshold"               │
│    active chats: 1                                   [Open] [Stop] [Peek]│
├──────────────────────────────────────────────────────────────────────────┤
│  ○ Test (self-chat)     :101  STOPPED                                    │
│    last activity yesterday 21:40                    [Open] [Start] [Peek]│
└──────────────────────────────────────────────────────────────────────────┘
```

Per row, and where each value comes from:

| Element | Source |
|---|---|
| Name | `config.yaml` `brand.name` (new key), fallback directory name |
| Display | `config.yaml` `window.display` (new key, e.g. `":99"`) |
| Status pill + state word | §3.4 rule over `status.json` |
| Uptime | `now - started_at` |
| Last activity | `MAX(ts) FROM messages` |
| Unread now | `status.json.unread_badge` |
| Replies / flagged today | `status.json.counts_today` (phase 1: `COUNT(*) WHERE role='assistant' AND ts >= today`) |
| Active chats | `COUNT(DISTINCT customer) WHERE ts > now-30min` |
| Last error | `status.json.last_error`, else last `ERROR`/`WARNING` line of the log |

Status colours: green RUNNING, grey STOPPED, amber off-hours, red STUCK/error.
No charts. No sparklines. A red row is the alert mechanism.

### 4.2 Brand detail (`/#/brand/<id>`)

Data: `GET /api/brands/<id>/chats` (customer list),
`GET /api/brands/<id>/chats/<customer>` (thread + customer + orders),
`GET /api/brands/<id>/log?n=50`.

```
┌────────────────────┬─────────────────────────────────────────────────────┐
│ ← Tacos El Nico    │  +52 55 1234 5678  · Juan · first seen 12 Aug       │
│ RUNNING idle       │  notes: sin cebolla siempre                         │
├────────────────────┤  recent orders: 2 al pastor (new, 09:10) · ...      │
│ ▸ Juan        9:12 ├─────────────────────────────────────────────────────┤
│   "sí, 2 al pas…"  │                                                     │
│ ⚑ +52 55 9876  9:05│         [user]  hola, tienen al pastor?     09:08   │
│   flagged >500     │  09:09  gpt: sí claro! ¿cuántos quieres?  [asst]    │
│   Rosa        8:41 │         [user]  2 sin cebolla                09:10   │
│   Pedro   yesterday│  09:10  gpt: va, 2 al pastor sin cebolla … [asst]   │
│                    │                                                     │
│                    ├─────────────────────────────────────────────────────┤
│                    │  log (last 50)                                      │
│                    │  09:10 INFO Sent reply to +52 55 1234 5678: va, …   │
│                    │  09:05 INFO Flagged, not sent (over_threshold): …   │
└────────────────────┴─────────────────────────────────────────────────────┘
```

- **Left column, chat list:** `SELECT customer, MAX(ts), last content` grouped
  by customer, newest first. Snippet = last message content truncated. The
  flag marker comes from `status.json.last_flag` (phase 2) or a log grep
  (phase 1); a `flags` table is deliberately *not* added — the log is the
  record.
- **Right top, customer card:** the `customers` row + `recent_orders(n=5)`.
  Notes are shown, not edited (punted).
- **Right middle, thread:** `messages WHERE customer=? ORDER BY ts` last 100,
  rendered as two bubble styles by `role`. Newest at the bottom, auto-scroll
  unless the user scrolled up. This is the audit surface: what did the bot
  say, to whom, when.
- **Right bottom, log tail:** the brand's `ventanita.log`, monospace. This is
  the 2am panel. It is not filtered per customer; it is the raw file, because
  that is what the owner would `tail` anyway.
- **Header buttons:** Stop/Start, Peek (opens the live screenshot in a modal,
  refreshes every 2 s while open).

Read-only. There is no reply box. Sending from the console is punted (§8): the
human intervenes by opening the real WhatsApp on their phone, which is already
linked to the same account.

## 5. "Add a brand" — what actually happens

The wizard is the existing manual ceremony (`start_isolated_display.sh` → peek
screenshot → scan QR → `calibrate.py` → `ventanita`) with the console pressing
the keys. Nothing new is invented; two gaps in the existing scripts are fixed.

**Step 0 — form.** Name, persona text (goes into `brain` config), menu file
(uploaded/pasted, written to `menu.txt`), optional allowed-chats list. Console
picks the next free display (`:99`, `:100`, … — check `/tmp/.X<N>-lock`) and
slugs the name into `brand_id`.

**Step 1 — create the directory.** Copy `config.example.yaml` → `brands/<id>/config.yaml`,
set `brand.name`, `window.display`, relative `paths:`. Create empty
`browser-profile/`.

**Step 2 — isolated display + browser.** Run `scripts/start_isolated_display.sh`
with `VENTANITA_VDISPLAY=:N` and a new `VENTANITA_PROFILE_DIR=brands/<id>/browser-profile`.
The script gains one flag: `--user-data-dir="$VENTANITA_PROFILE_DIR"`.
**This is required, not optional:** today the script launches the browser with
the default profile, so two brands would share one WhatsApp Web login. A
per-brand profile is what makes "scan once, forever" true per number.

**Step 3 — QR.** The wizard page shows `peek.png` for that display refreshed
every 2 s (same endpoint as the Peek button). The owner scans it with the
brand's phone. Detection of "linked" is a button: **"I scanned it, continue"**.
Auto-detecting the chat list via OCR is possible and punted; the human is
right there.

**Step 4 — calibration.** Two paths, tried in order:

1. **Copy a known-good calibration.** Xvfb is a fixed `1920x1080` and the
   browser is `--start-maximized`, so *every brand on the same machine has
   identical coordinates*. The frozen world is more frozen inside Xvfb than
   on a real desktop. The wizard copies the `window:` block from the newest
   existing brand (or from `calibration.default.yaml` in the repo, checked in
   once it is known good for the pinned browser/zoom), then shows `peek.png`
   with the six rectangles/points drawn over it in JS and asks "do the boxes
   line up?"
2. **Click-to-calibrate.** If not, the wizard shows `peek.png` at 1:1 and
   walks the *same eleven prompts in the same order as `calibrate.py`*, but
   the point source is a click on the image (`event.offsetX/Y`) instead of
   `pyautogui.position()`. To share the writer, `calibrate.py` is split into
   `collect_points(ask)` and `write_window_config(config_path, points)`; the
   CLI passes `ask = hover-and-Enter`, the console passes the eleven
   clicked coordinates. Same keys, same file, one code path writing it.

**Step 5 — start.** Same as the Start button (§3.5). Brand appears in the
overview within one poll.

**Step 6 (optional) — self-chat week.** The form's allowed-chats field
defaults to the brand's own "message yourself" chat, matching the sandbox
rule in `buildplan.md` §5. The owner clears it when ready.

After reboot, Xvfb is gone. The Start button's launcher re-runs
`start_isolated_display.sh` (it already `pgrep`s for an existing Xvfb and
reuses it), which relaunches the browser on the saved profile; WhatsApp Web
comes back logged in. That covers the common case without systemd. A proper
boot-time unit is punted.

## 6. Code layout

One file per concern, matching the bot:

```
src/ventanita/
  status.py               # write(path, **fields): atomic status.json   (bot side, ~20 lines)
  dashboard/
    server.py             # http.server, routes → JSON; --browser / --port flags
    brands.py             # discover brands/, read status/config, start/stop/peek
    queries.py            # the six read-only SQL queries the screens need
    wizard.py             # add-a-brand steps 1–5 (shells out to the scripts)
    ui.html               # the whole UI: inline CSS + vanilla JS
  calibrate.py            # split into collect_points() + write_window_config()
scripts/
  start_isolated_display.sh   # + --user-data-dir, honours VENTANITA_PROFILE_DIR
```

Entry point: `ventanita-dashboard = "ventanita.dashboard.server:run"`.
`run()` starts the server thread, then `webview.create_window("Ventanita",
url)` + `webview.start()` if pywebview imports, else prints the URL and opens
`xdg-open`. A `ventanita.desktop` file in `scripts/` for the app menu.

Target size: server+brands+queries+wizard ≈ 400 lines Python, `ui.html` ≈
300 lines. If it goes past ~1000 total, something is being overbuilt.

Tests: `queries.py` against a temp DB (same style as `tests/test_db.py`);
`brands.py` status rule against fixture `status.json` files. The HTML is not
unit-tested; it is opened in a browser.

## 7. Phased build plan

Each phase ships on its own and is useful on its own.

### Phase 1 — read-only console against today's single brand (no bot changes)

- `dashboard/server.py`, `queries.py`, `ui.html`, `ventanita-dashboard` entry.
- Brand discovery: `brands/*/config.yaml`, else the repo root as one brand.
- Overview + detail screens, all data from the DB + log file. "Running" =
  `pgrep`. Counts from `messages`.
- `--browser` mode first, pywebview window second (same page).
- Exit criterion: the owner can open the app, see the self-chat thread the bot
  had this morning, and read the log without a terminal.

### Phase 2 — multi-brand layout + heartbeat + buttons (small bot changes)

- `--config` / `VENTANITA_CONFIG`, paths relative to the config file.
- `status.py` + the fifteen lines in `main.py`; `unread_badge` from trigger;
  `counts_today`; `last_error` from a `try/except` around the loop body that
  logs and continues instead of crashing.
- `PRAGMA journal_mode = WAL` in `db.connect()`.
- `brand.name`, `window.display` config keys.
- Console: status rule from §3.4, Start/Stop/Peek, `brands/` directory as the
  primary layout. Migration for the existing install: `mkdir brands/<name>`
  and move four files; a one-off `ventanita-migrate` is *not* written — the
  README shows the `mv`.
- Exit criterion: two brands (a real one and the self-chat sandbox) on `:99`
  and `:100`, both visible, Stop kills one without touching the other.

### Phase 3 — "Add a brand" wizard

- `start_isolated_display.sh` gains `--user-data-dir`.
- `calibrate.py` split; `calibration.default.yaml` checked in once verified.
- `wizard.py` + the wizard section of `ui.html`: form → dir → display → QR
  peek loop → copy-or-click calibration with overlay check → start.
- Exit criterion: the owner links a brand-new number without a terminal, and
  the bot replies in that number's self-chat within the hour.

Phase 1 can start today against the v0.2.1 tree without colliding with the
concurrent bug-fix work, because it touches no file under `src/ventanita/*.py`
except adding a new `dashboard/` package.

## 8. Explicitly out of scope for v0.3

Called out so nobody builds them by accident. "The atom first" still applies.

- **Sending or editing messages from the console.** It is a viewer. The owner's
  phone is the intervention tool.
- **Editing persona, menu, allowed-chats, timings in the UI.** They are text
  files; edit them and restart. A "reveal in file manager" button is fine.
- **Auto-restart / watchdog / boot-time start.** Red row + Start button. If it
  becomes a real problem, a systemd user unit per brand, not console logic.
- **Remote access, auth, HTTPS, LAN binding.** `127.0.0.1` only. `ssh -L` exists.
- **Packaging** (`.deb`, AppImage, Flatpak). `pip install -e ".[dashboard]"` +
  a `.desktop` file.
- **Windows / macOS.** Xvfb and xdotool are Linux; so is this.
- **A `brand_id` column / shared DB / cross-brand reports.** Per-brand files.
  `ATTACH` later if a report is ever wanted.
- **A `flags` table.** Flags live in the log and in `status.json.last_flag`.
- **Charts, sparklines, "analytics."** Counts and a red row.
- **Notifications** (desktop popups, sound). Open the window.
- **Auto-detecting the QR scan.** A button that says "I scanned it."
- **Real customer identity in `messages.customer`.** Bot-side work (read the
  chat-row label already OCR'd for the allowlist, use it as the key). It is
  the single biggest thing standing between the detail screen and being
  genuinely useful, but it belongs to the bot's own changelog, not this doc.
- **Several chats going unread in one detection window.** Known bot
  limitation from 0.2.1; unrelated to the console.
- **Theming.** One dark theme, matching the pinned WhatsApp window.

Still no framework. Still one file per job. Still readable in one sitting.
